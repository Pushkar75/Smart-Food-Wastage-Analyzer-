# Hostel Mess Attendance ML — Versioned Retraining + Real Attendance Feedback

This project keeps the existing XGBoost Poisson forecasting pipeline and adds:

1. Automatic model versioning (`v1`, `v2`, `v3`, ...).
2. Prediction snapshots saved when `/predict` is called.
3. A `/record-attendance` endpoint for the fingerprint/backend to submit the real attendance later.
4. Automatic completion/appending of the prediction row into the CSV.
5. Protection against accidentally recording the same prediction twice.
6. Robust handling of CSVs where Excel has stored numbers with a leading `'`.
7. The original prediction response remains compatible: it still returns predicted attendance and its interval.

# 5. What happens automatically after `/predict`

The ML service saves a snapshot:

```text
prediction_snapshots/
    2026-09-17_breakfast_a81f3c2d.json
```

That snapshot contains:

- the exact feature inputs used by the model
- prediction
- lower/upper interval
- prediction date
- model version
- prediction ID
- prediction timestamp

This is important because the CSV row must represent what the model actually knew at prediction time.

For example:

```text
6:00 AM

YES = 720
NO = 130
No response = 286

          ↓

MODEL PREDICTION
```

If students change their answers at 6:30 AM, the historical record of the 6:00 AM prediction does not change.

# 6. After the fingerprint scan

When the meal finishes, your backend/fingerprint service knows:

```text
actual_attendance = 792
```

Call:

```text
POST /record-attendance
```

with:

```json
{
  "prediction_id": "2026-09-17_breakfast_a81f3c2d",
  "actual_attendance": 792
}
```

The ML service:

```text
prediction_id
      ↓
find snapshot
      ↓
add actual_attendance
      ↓
append completed row to CSV
      ↓
delete snapshot
```

The response is:

```json
{
  "status": "recorded",
  "prediction_id": "2026-09-17_breakfast_a81f3c2d",
  "actual_attendance": 792,
  "model_version": 1
}
```

The snapshot is deleted only after the CSV write succeeds.

If the same prediction is submitted twice, the API returns `409` instead of silently creating a duplicate row.

---

# 7. CSV after recording

The completed row will contain the prediction-time features plus:

```text
prediction_id
model_version
actual_attendance
```

`prediction_id` and `model_version` are audit/bookkeeping fields. They are NOT used as ML features.

For example:

```text
prediction_id,date,meal,...,predicted_attendance,lower_bound,upper_bound,actual_attendance,model_version
2026-09-17_breakfast_a81f3c2d,2026-09-17,breakfast,...,785,760,808,792,1
```

The next training run reconstructs target-derived historical features from completed `actual_attendance` values, rather than blindly trusting old precomputed historical-feature columns.

That prevents future/current target leakage.

# 8. Monthly retraining

You do not need to manually create a new training script.

Every month:

```powershell
python -m src.train
```

The process is:

```text
Existing CSV
     +
new fingerprint-labelled rows
     ↓
leakage-safe feature reconstruction
     ↓
chronological train/validation/test
     ↓
time-aware hyperparameter tuning
     ↓
XGBoost Poisson training
     ↓
new automatic version
```

For example:

```text
September → v1
October   → v2
November  → v3
December  → v4
```

Each version is trained using the complete available historical CSV.

# 9. CSV apostrophe issue

Some CSV files exported through Excel can contain values such as:

```text
'1200
'64
'0.748
```

The leading apostrophe is generally an Excel "treat this as text" marker.

The supplied CSV has been saved as normal CSV numeric values, so it does not contain those leading apostrophes.

The loader also defensively removes a leading `'` before numeric conversion.

Therefore both of these are accepted safely:

```text
1200
'1200
```

and become the numeric value:

```text
1200
```

The new CSV writer also writes numeric values normally, without adding leading apostrophes.

---

# 10. Do not manually calculate historical features for new rows

This is important.

When the fingerprint result arrives, you only need to send:

```text
prediction_id
actual_attendance
```

Do NOT calculate:

```text
rolling_7_attendance
prev_same_meal_7d
historical_same_weekday_attendance
```

at that point.

Those values were already stored in the prediction snapshot because they represent the information available at prediction time.

When the model is retrained later, the training pipeline reconstructs the historical features from the complete chronological attendance history.
